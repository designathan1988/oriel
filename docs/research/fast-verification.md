# Fast verification without full suites

Verification in seconds for FORMA 3 does not come from running the same suites faster. It comes from changing **what** is verified on each change: the model state and runtime errors, not identical pixels rendered on the CPU. The mature editors built on top of graphics engines (tldraw, Excalidraw, VS Code) test the document and the state machine without rendering, and leave image comparisons to separate batches, with tolerance and outside the loop of each change. The engines (three.js, Babylon.js) use pixels because pixels are their product, and even so with margins and in sharded CI. For this project, the recipe is a chain of four cheap checks. The first is types, with TypeScript 7, 8 to 12 times faster. The second is unit tests chosen by Vitest's recorded dependency graph. The third is a *replay* of command logs with a model hash, without a browser. The fourth is a **single-page** smoke test that walks through the scenes via a test API, checks counts, hash and error list, and takes no screenshot. The 15 pixel-exact scenes in SwiftShader and the 40 flows leave the per-change routine and instead run at the close of a stage, on pre-push or overnight. The plan's estimates add up to **about 10 to 15 s** per change, versus the current minute of `npm run check`. The price is accepting, as Meta and Datadog accept, a small and measured rate of regressions that only show up in the next full run.

## The bottleneck is the CPU rasterizer, not the number of tests

The current `npm run check`, wired to the Claude Code Stop hook via `scripts/gate.mjs`, runs types, unit tests and the 15 visual scenes. The script's own comment estimates about 5 s per scene and a total under one minute. The scenes are compared with `threshold: 0, maxDiffPixels: 0` in SwiftShader, because only the software rasterizer guarantees the same pixels on every run. That choice has a rationale: the configuration records that the three.js margin let through textured materials 3% darker. The cost, however, is structural. Microlink measured **about 24 s per 3D page in SwiftShader, versus about 6 s in Mesa llvmpipe**, and 2 to 3 s on 2D pages. Some requests in SwiftShader timed out ([Microlink](https://microlink.io/blog/webgl-without-a-gpu)). Chromium, in addition, is retiring the automatic fallback to WebGL on SwiftShader: it is "a high security risk due to JIT-ed code running in Chromium's GPU process", and context creation "will soon fail instead of falling back". That is why `--enable-unsafe-swiftshader` is already required ([Chromium swiftshader.md](https://chromium.googlesource.com/chromium/src/+/main/docs/gpu/swiftshader.md)). There is also Playwright's `toHaveScreenshot`, which waits for "two consecutive page screenshots match" before comparing with the reference. Each scene therefore pays for at least two CPU captures ([Playwright PageAssertions](https://playwright.dev/docs/api/class-pageassertions)).

The obvious alternative, using the real GPU, trades determinism for speed. Pixels vary with driver, vendor and ANGLE backend. Since 1.49, Playwright uses `chromium-headless-shell` by default. With `channel: 'chromium'` it uses the new headless, whose "GPU/WebGL availability, features and performance will vary" ([Playwright #33566](https://github.com/microsoft/playwright/issues/33566)). Microlink found out the hard way that, without a display, WebGL silently fell back to 2D, returned HTTP 200 and even ran about 1 s *faster* than the correct render. Today its CI asserts the renderer identity as part of the test ([Microlink](https://microlink.io/blog/webgl-without-a-gpu)). The practical conclusion for the project is to separate roles. The real GPU serves for **state** checks, fast and tolerant of pixel variation, and the test fails immediately if `UNMASKED_RENDERER_WEBGL` contains "SwiftShader" or "llvmpipe". Exact SwiftShader is restricted to the full visual suite, which is rare. One point remains unconfirmed: there is no primary source with times measured on a real GPU side by side with SwiftShader for the same page, nor documentation of the behavior of `--use-angle=d3d11` in the Windows headless shell. That is settled with a single measurement.

None of the projects studied runs pixels as a pre-commit check. three.js compares all examples against reference JPEGs, with a threshold of 0.1 per pixel and at most 0.1% of pixels different. It runs on software Vulkan (lavapipe), split into 5 CI jobs, with a 5 s render timeout and a list of examples excluded for "Take too long" ([three.js puppeteer.js](https://github.com/mrdoob/three.js/blob/dev/test/e2e/puppeteer.js)). In Babylon.js the visualization tests are declarative, by Playground ID, and the team itself admits occasional false positives ([Babylon docs](https://doc.babylonjs.com/contribute/toBabylon/HowToContribute); [Babylon forum](https://forum.babylonjs.com/t/testing-babylon-projects/32604)). Excalidraw's test workflow is a single job, `yarn test:app`, with no e2e or visual regression ([excalidraw test.yml](https://raw.githubusercontent.com/excalidraw/excalidraw/master/.github/workflows/test.yml)). tldraw's agent guide marks running the whole repository as "slow, avoid unless necessary" and says to "run the smallest relevant suite" ([tldraw AGENTS.md](https://raw.githubusercontent.com/tldraw/tldraw/main/AGENTS.md)).

## Static checks and selection cut the time in half, with known blind spots

The static layer is the cheapest and the one that improved the most in 2026. **TypeScript 7.0, the native Go version, shipped stable on July 8, 2026** as the regular `tsc`. It type-checks 8 to 12 times faster with default settings. Projects similar to this one dropped from 11.2 s to 1.46 s (tldraw) and from 12.8 s to 1.47 s (playwright), with the same results as 6.0 ([TS 7.0](https://devblogs.microsoft.com/typescript/?p=5246)). For this repository the migration is low risk. The `tsconfig.json` already declares `types: ["node"]`, which neutralizes the trap of the new `types: []` default. It uses `moduleResolution: "Bundler"` and has no `baseUrl`. There is also no ESLint, so the lack of a programmatic API until 7.1 affects nothing. There are two points to watch: `.tsbuildinfo` files do not carry over from one version to another, and full support for `--incremental` in 7.0 has not been confirmed. Since Vite only transpiles, the dev server serves code with type errors without complaining. `tsc --noEmit` remains mandatory ([Vite features](https://vite.dev/guide/features.md)). Oxlint with type checking, stable since July 22, 2026, covers 59 of the 61 typed typescript-eslint rules and runs 12 to 18 times faster. According to the vendor, `--type-check` also reports compiler errors in the same pass ([Oxc](https://oxc.rs/blog/2026-07-22-type-aware-linting-stable)). Rules such as `no-floating-promises` and `no-misused-promises` catch real worker and IndexedDB bugs that `tsc` does not. Even so, they are an optional addition, not a prerequisite.

Test selection is where the project can save the most, and also where the tools mislead most easily. `vitest related` and `vitest --changed` choose tests by Vite's module graph. By default that graph is static and **does not see dynamic imports** ([Vitest CLI](https://vitest.dev/guide/cli)). Starting with **5.0.4** (the project is on 5.0.3) there is `experimental.recordDependencies`. It records the modules each test actually loaded, including the dynamic imports that executed, and stores them in `dependencies.json`. The gaps are documented: files read with `fs`, externalized modules, mocks with a factory and dynamic imports on paths that were not executed. Selection errs toward "extra tests but never fewer" when the problem is isolation, and changes to the config or the global setup trigger everything ([Vitest experimental](https://vitest.dev/config/experimental)). The complement is `forceRerunTriggers`: any file outside the graph listed there (worker entry, shaders, atlas, fixtures read by `fs`) forces the whole suite ([forceRerunTriggers](https://vitest.dev/config/forcereruntriggers)).

Playwright deserves the opposite warning. `--only-changed` runs the changed specs and those that *import* changed files ([release notes](https://playwright.dev/docs/release-notes)). Reading the local 1.64 code shows that this graph comes only from what the Node runner loads: specs, fixtures and helpers. The application code served by `webServer` is left out. An edit in `src/f3/**` selects **zero tests and exits with code 0**. That is false confidence, and that is why the recommendation is not to adopt it.

Industrial evidence confirms that selection works, as long as there are full runs as a safety net. Meta's predictive selection cuts infrastructure cost in half and still catches **more than 99.9% of faulty changes and more than 95% of individual failures** ([arXiv 1810.05286](https://arxiv.org/abs/1810.05286)). In production, it ran about a third of the dependent tests ([Meta Engineering](https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/)). Datadog TIA uses per-test coverage. It forces everything when a "tracked file" changes, such as `package.json`, and never skips tests on the default branch. It also admits it does not detect changes in dependencies, compiler options and data files ([Datadog TIA](https://docs.datadoghq.com/tests/test_impact_analysis/)). The common pattern is always the same: a fast subset on each change, full-run triggers and a periodic full run. There is no published error-rate data for Vitest's `--changed` on small projects.

## State, replay and invariants replace most of what the scenes catch

The highest-leverage change is to start asserting state instead of pixels, with the same mechanism that `visual.spec.ts` already has halfway. The spec already freezes `Math.random`, `crypto.randomUUID` and the clock, waits for `View.settled`, collects `pageerror` and `console.error`, and compares draw calls and triangles against per-scene ceilings. What remains is to extract that part into a screenshot-free smoke test: **one browser, one page, one load**, with scenes switched through a DEV API (`window.__f3.loadScene`, `settled()`, `stats()`). `stats()` returns entity, call and triangle counts, a canonical hash of the evaluated model and `errors[]`. This is the three.js design, which waits for a `_renderFinished` flag instead of sleeping. It is also tldraw's, whose e2e skill says to navigate once, reset quickly and use `page.evaluate()` instead of keyboard shortcuts ([tldraw write-e2e-tests](https://raw.githubusercontent.com/tldraw/tldraw/main/skills/write-e2e-tests/SKILL.md)). This smoke test catches shaders that do not compile (with `renderer.debug.checkShaderErrors` and `onShaderError`), unhandled exceptions and rejections, context loss, empty scenes, draw-call explosions and geometry changes. It **does not catch** subtle variation in color, material or lighting, such as the 3% regression that motivated the zero threshold. That risk remains covered by the exact scenes, just at a different time.

Below the browser sits the model's *golden master*. Factorio computes a CRC of the whole map on every tick and flags the first divergent tick ([FFF #47](https://factorio.com/blog/post/fff-47)). Its integration tests compare CRCs against saved values, regenerated when the logic changes on purpose. Its unit tests do not load graphics and are "really fast" ([FFF #60](https://factorio.com/blog/post/fff-60)). Here that becomes command logs in JSON, re-executed in Vitest against `src/f3/eval/*` and `manifold-3d` in WASM, without WebGL, with one snapshot per step of a canonical serialization (sorted keys, rounded floats) or of its hash ([Vitest snapshot](https://vitest.dev/guide/snapshot)). Figma offers a property to check for free: undoing, copying and redoing up to the present leaves the document the same. Its IDs are counter plus client, deterministic and without random UUIDs ([Figma multiplayer](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). Onshape shows the ceiling of this idea. Before each release, bots regenerate "millions of Documents" and report shape changes. That is how they found a Unicode encoding regression in sketch text that the "handcrafted automated tests" let through ([Onshape](https://www.onshape.com/en/blog/how-onshape-delivers-safe-continuous-deployment)). The sample projects and the scenes in `e2e/scenes.ts` are the equivalent local corpus.

Runtime invariants make every run, whether manual, e2e or by a user, work as a test. Chromium keeps cheap CHECKs in all builds and leaves O(n²) checks in DCHECK, development only ([Chromium checks.md](https://chromium.googlesource.com/chromium/src/+/main/styleguide/c++/checks.md)). Unreal has `ensure`, which reports and continues, only on the first failure of the session ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/asserts-in-unreal-engine)). SQLite turns off asserts in release because they would make the database "about three times slower" ([sqlite.org](https://sqlite.org/assert.html)). Microsoft found significantly lower fault density in files with more assertions ([MSR-TR-2006-54](https://www.microsoft.com/en-us/research/publication/assessing-the-relationship-between-software-assertions-and-code-qualityan-empirical-investigation/)). In FORMA 3 this means three pieces. The first is a `validateDocument()` behind `import.meta.env.DEV` at the end of each command: valid IDs, no NaN, walls connected to existing nodes. The second is paired validation before writing to IndexedDB and right after reading, in the TigerBeetle style ([TIGER_STYLE](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/TIGER_STYLE.md)). The third is treating manifold's `status() !== NoError` as a logged error ([ManifoldCAD ErrorStatus](https://manifoldcad.org/docs/jsuser/types/ErrorStatus.html)). Untrusted input, such as IFC, DXF, OSM or saved JSON, goes through ordinary validation and never through an assert.

## Generators and production catch what no hand-written suite catches

fast-check runs 100 cases per property by default. `interruptAfterTimeLimit` caps wall-clock time, and the fuzzing recipe in the documentation is `numRuns: Infinity` for 10 minutes ([fast-check timeouts](https://fast-check.dev/docs/configuration/timeouts/)). `fc.commands` with `modelRun` directly models a command editor with undo. Shrinking works on the commands that actually ran, and `seed` + `path` + `replayPath` reproduce the failure exactly ([fast-check model-based](https://fast-check.dev/docs/advanced/model-based-testing/)). The bug classes it has already found in real libraries are exactly those of a CAD: `-0`, `5e-324` and asymmetric stringify→parse round trips ([track record](https://fast-check.dev/docs/introduction/track-record/)). The most relevant concrete case is Manifold itself. Issue #1888, opened on October 14, 2026, shows the union of two stacked boxes losing 8% of the volume with `Status()` equal to `NoError`, and `a + b` different from `b + a`. The cause is offsets of about 3e-11 ([manifold#1888](https://github.com/elalish/manifold/issues/1888)). #1897 came from fuzzing with jitter of 1 to 8 times the tolerance and hung in 4 of 9 runs ([manifold#1897](https://github.com/elalish/manifold/issues/1897)). Walls touching slabs and openings flush with the face fall exactly on that boundary. That is why properties of volume (vol(A∪B) ≈ vol(A)+vol(B)−vol(A∩B)), commutativity and watertightness are worthwhile, with coordinates on the project grid and occasional jitter. The industry lessons (Dropbox, FoundationDB, TigerBeetle) point the same way. Dropbox gained about 10 times more runs by swapping the native file system for an in-memory one, and runs "tens of millions" of random cases per night ([Dropbox](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)). The equivalent here is running without a browser and with a single seed. In the fast loop, the cost is configurable, with something like 100 cases and a 5 s ceiling. Overnight, with 10 minutes.

Production catches the last class of problems: GPU diversity. Figma reads back pixels rendered into a texture to detect faulty drivers at runtime. At the WebGPU launch, it discovered mid-session failures on Windows that load tests and prior blocklists did not catch ("was not enough"). Only a percentage rollout, with metrics per GPU, OS and browser, and a dynamic fallback to WebGL solved it ([Figma WebGPU](https://www.figma.com/blog/figma-rendering-powered-by-webgpu/)). For a one-developer SaaS, the proportional version is Sentry with `replaysOnErrorSampleRate: 1.0` and session sampling near zero ([Sentry Replay](https://docs.sentry.io/platforms/javascript/session-replay/)), `hidden` source maps deleted after upload ([Sentry Vite](https://docs.sentry.io/platforms/javascript/sourcemaps/uploading/vite/)) and `beforeSend` scrubbing user data ([Sentry filtering](https://docs.sentry.io/platforms/javascript/guides/react/configuration/filtering/)). The free plan has 5 thousand errors per month ([Sentry pricing](https://sentry.io/pricing/)). Canvas recording has no masking, and clients' floor plans and addresses may be personal data under the LGPD. That is why the safest option is to attach the command JSON instead of the pixels. No legal source was read, so this point needs review.

| Technique | Catches | Does not catch | Cost per change |
|---|---|---|---|
| `tsc` (TS 7) | contracts, nulls, broken refactoring | logic, render, runtime | ~1–2 s (estimate from the benchmarks) |
| Oxlint with types | floating promises, incomplete `switch` | the same things tsc does not catch | ~1 s (vendor) |
| `vitest --changed` with recorded dependencies | logic affected by the diff | files read by `fs`, worker code not executed | ~1–4 s (estimate; today it is 10 s) |
| Command replay + hash | model and evaluation regression, determinism | render, UI, GPU | ~1–2 s (estimate) |
| State smoke on one page | shader, exceptions, lost context, counts, geometry | color and material nuance, panel layout | ~5–8 s (estimate, to be measured) |
| DEV invariants | silent corruption at the moment it occurs | what no executed path touches | ~0 s extra |
| Bounded fast-check | numeric edges, round trips, manifold degeneracies | what the generator does not produce | configurable ceiling (~5 s) |
| Exact scenes + 40 flows | everything visual and gesture-related | different real GPUs | minutes, outside the routine |
| Sentry in production | drivers, real data, mid-session failures | nothing before deploy | 0 s locally |

## Conclusion

The central point is that the determinism that today justifies exact SwiftShader can be applied further down, in the model, where it is cheap. A canonical hash of the evaluated document is as exact as a pixel-by-pixel comparison and more exact than it about geometry. It costs milliseconds and is GPU-independent. Pixels are left with the only job that only they do, appearance, and that job does not need to happen on every edit. The second lesson is that badly configured fast verification is worse than slow verification. `--only-changed` exiting with zero tests, the static graph that ignores dynamic imports and WebGL falling back to 2D with HTTP 200 give a false green signal. Every fast layer needs a sanity test of itself: assert the renderer, force the full run via triggers, count the selected tests. The real gain only exists if the full run keeps happening at a fixed cadence.

## Prioritized plan for FORMA 3

The seconds below are estimates derived from the sources and the current state of the repository. Step 1 includes measuring each one once and recording the result in `scripts/check.mjs` itself, as it already does with per-stage times.

| # | Step | How, in this stack | Seconds per change | Leaves the routine |
|---|---|---|---|---|
| 1 | Separate `check:fast` from `check:full` | `scripts/check.mjs --fast`: types + selected unit tests + replay + smoke; the Stop hook (`scripts/gate.mjs`) and pre-commit switch to calling `--fast`; `--all` becomes the full run | 0 (reorganization) | The 15 pixel-exact scenes leave the Stop hook and pre-commit |
| 2 | State smoke on one page | `window.__f3` API in DEV only (`loadScene`, `settled`, `stats` with counts, ceilings and hash, `errors[]`); one Playwright spec in a project with `testProject.default: false` on visual; real GPU with a `UNMASKED_RENDERER_WEBGL` check; a single PNG of the scene for the touched area, for the visual analysis required by CLAUDE.md | ~5–8 | Screenshots of every scene on each edit; waiting for two identical frames |
| 3 | Command replay with golden master | `test/unit/replay.test.ts` reads JSON logs from the scenes and sample projects, re-executes them in the model and in `eval`, and compares a per-step hash snapshot; counter-based IDs and fixed seed | ~1–2 | Opening the browser to check for model regression |
| 4 | Invariants and sentinel | `validateDocument()` in DEV at the end of each command and paired in IndexedDB; `ensure()`; `checkShaderErrors`/`onShaderError`, `webglcontextlost`, manifold's `status()` and worker errors (`postMessage`) feed `errors[]` | ~0 | Manual console inspection |
| 5 | Selective Vitest | Upgrade to ≥5.0.4; `experimental.recordDependencies: true`; one full run to generate the baseline; `vitest --changed --run --bail=1`; `forceRerunTriggers` with the worker entry, `src/**/*.glsl`, atlas and fixtures read by `fs`; full run after changing imports | ~1–4 (today ~10) | Full `vitest run` on each edit |
| 6 | TypeScript 7 | `npm i -D typescript@7`; check the `tsconfig` against the removed options (the `types` are already explicit); measure `--incremental`; optional: `oxlint --type-aware --type-check` as a single pass | ~1–2 (estimated) | — |
| 7 | Properties with fast-check | undo∘do = identity, save→load→save byte for byte, manifold volume, commutativity and watertightness on the grid with jitter; `numRuns: 100` with `interruptAfterTimeLimit: 5_000` in fast; 10 min in the nightly run | ~2–5 (ceiling) | — |
| 8 | Full-run cadence | `check --all` (exact scenes in SwiftShader + 40 flows) on pre-push, at stage close and overnight; each flow only with `-g` for the touched feature; no retries, intermittent failures go to quarantine with a reason | 0 per change | The 40 flows of every verification; Playwright's `--only-changed` (do not adopt) |
| 9 | Production | Sentry with replay on error only, no canvas, `beforeSend` scrubbing the user, release tags and alerts for `ensure`, lost context and `QuotaExceededError` | 0 locally | Relying on tests alone for GPU diversity |

Adding up steps 2, 3, 5, 6 and 7, the fast loop comes to **about 10 to 15 s, with a 20 s ceiling**, versus about one minute for the current `npm run check`. Coverage of exact appearance and gestures does not decrease, it only moves to a different time. The implementation order follows gain per effort. Steps 1 and 2 remove the largest share of time at once. Steps 3 and 4 make up for the loss of visual signal with a more precise state signal. Steps 5 to 7 are optimizations and hardening. Step 9 covers what no local test reaches.
